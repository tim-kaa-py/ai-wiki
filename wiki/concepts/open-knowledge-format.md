# Open Knowledge Format (OKF)

**OKF** is an open, vendor-neutral format (v0.1, draft, from Google Cloud's `knowledge-catalog` project) for representing *knowledge* — the metadata, context, and curated insight around data and systems — as a directory of markdown files with YAML frontmatter. It is designed to be authored by people, generated by agents, exchanged across organizations, and consumed by both, with no schema registry, no central authority, and no required tooling: "if you can `cat` a file, you can read OKF; if you can `git clone` a repo, you can ship it."

OKF is best understood as the **specified** counterpart to the informal [LLM Wiki Pattern](llm-wiki-pattern.md) — it pins down the minimal rule set two independent tools must agree on to exchange a knowledge corpus, while deliberately declining to dictate tooling.

## The Central Design Bet: Standardize the Minimum

OKF's whole thesis is that the *format* is the contribution and almost everything else should be left unspecified. It standardizes only the small set of structural conventions needed to make a corpus **self-describing**, and treats anything beyond that as producer's choice.

**Goals:** define a format enrichment agents can write into; inform how consumption agents read/traverse it; facilitate exchange across systems and orgs; standardize the small number of required fields.

**Explicit non-goals:** defining a fixed taxonomy of concept types; prescribing storage/serving/query infrastructure; replacing domain schemas (Avro, Protobuf, OpenAPI) — OKF *references* them, it does not subsume them.

The reasoning chain:
- The space of agent knowledge representation is evolving fast, spawning many incompatible conventions.
- Knowledge is best held in commonly accessible formats: readable by humans without tooling, parseable by agents without bespoke SDKs, diffable in version control, portable across tools/orgs/time.
- Any rule beyond the self-describing minimum is a place a producer might reasonably want to differ — locking it down creates lock-in and premature taxonomy.
- **Therefore:** standardize only the core (frontmatter + `type` + reserved files) and leave the rest open → maximizes adoption and longevity.

## Core Structure

| Term | Definition |
|------|-----------|
| **Knowledge Bundle** | The unit of distribution: a self-contained, hierarchical directory tree of markdown documents. Ships as a git repo (recommended), a tarball/zip, or a subdirectory of a larger repo. Directory layout is domain-independent. |
| **Concept** | One unit of knowledge = one markdown document. May describe a tangible asset (table, API endpoint) or an abstract idea (metric, business process). |
| **Concept ID** | The file's path within the bundle minus `.md` (`tables/users.md` → `tables/users`). Identity is positional — there is no separate ID field. |
| **Link** | A standard markdown link asserting an (untyped) relationship between concepts. |
| **Citation** | A link to an external source backing a claim in the body. |

### Frontmatter — one required field

The only **required** field is `type`: a short, self-explanatory string (`BigQuery Table`, `Playbook`, `Reference`, …). Type values are *not* centrally registered; consumers must tolerate unknown types by falling back to generic rendering.

**Recommended-but-optional** (priority order): `title`, `description` (one sentence, feeds index/search snippets), `resource` (canonical URI of the underlying asset; absent for abstract concepts), `tags`, `timestamp` (ISO 8601 last-meaningful-change). Producers MAY add arbitrary extra keys; consumers SHOULD preserve unknown keys on round-trip and MUST NOT reject documents for having them.

### Reserved filenames

`index.md` and `log.md` have defined meaning at *any* directory level and must not be used as concept documents. Everything else `*.md` is a concept.

- **`index.md`** — enumerates a directory's contents for **progressive disclosure** (see what exists before opening documents). Carries **no frontmatter**, with one narrow exception: the bundle-root `index.md` may declare `okf_version: "0.1"` — the only place frontmatter is permitted in an index. Body is sections of `* [Title](url) - description` bullets, description pulled from each concept's frontmatter.
- **`log.md`** — change history as ISO-8601 date-grouped entries, newest first, with a bold leading word (`**Update**`, `**Creation**`, `**Deprecation**`) that is convention, not requirement.

### Cross-linking

Ordinary markdown links express relationships. **Absolute (bundle-relative) links** begin with `/` and are recommended (stable when a doc moves within its subdirectory); relative `./` links are allowed. Link semantics are **untyped** — the kind of relationship (joins-with, depends-on, parent/child) lives in the surrounding prose, not the link. Consumers must tolerate broken links: a dangling link is "not-yet-written knowledge," not an error.

### Citations

External sources backing body claims go under a `# Citations` heading, numbered. Links may be absolute URLs, bundle-relative paths, or paths into a `references/` subdirectory that mirrors external material as first-class concepts.

## Conformance and the Permissive Consumption Model

Conformance is defined **asymmetrically** — a few hard rules on producers, a MUST-NOT-reject list for consumers. This asymmetry is load-bearing, not politeness.

**A bundle is conformant (§9) if only three things hold:**
1. Every non-reserved `.md` has a parseable YAML frontmatter block.
2. Every frontmatter block has a non-empty `type`.
3. Present `index.md`/`log.md` follow their structural conventions.

**Consumers MUST NOT reject a bundle for:** missing optional fields, unknown `type` values, unknown extra frontmatter keys, broken cross-links, or missing `index.md` files.

Why the permissiveness matters: if bundles are partially generated by agents and continuously refactored, strict validation would reject exactly the in-progress states that are normal for a living corpus. The permissive model is what lets OKF "remain useful as bundles grow, get refactored, and are partially generated by agents."

## Why Markdown-in-Git (the "metadata as code" argument)

Representing knowledge as plain markdown+frontmatter in git buys properties hard to get from a service-owned metadata store:

- **Human- and agent-readable** — no SDK or query language between reader and content; an engineer can `cat` a concept, an LLM can ingest it verbatim.
- **Version-controllable out of the box** — pull requests, diffs, blame, review; knowledge curation becomes a normal software-engineering activity.
- **Portable, lock-in free** — a bundle is a directory; ship it anywhere that speaks files.
- **Structured + unstructured, deliberately split** — frontmatter for the few fields you query/filter/index (`type`, `resource`, `tags`, `timestamp`); body for the prose, schemas, and examples humans and LLMs actually read.
- **Composes with existing tooling** — Obsidian, Notion, MkDocs, Hugo, Jekyll already render markdown+frontmatter.
- **Progressive disclosure built in** — index files let an agent navigate one level at a time instead of loading the whole bundle into context.
- **Graph-shaped, not just tree-shaped** — cross-links express relationships richer than the directory's parent/child.

## Positioning Against Neighbors

OKF is intentionally close to LLM-wiki repositories, Obsidian/Notion-style personal knowledge tools, and "metadata as code" approaches. It differs primarily in being **specified** — it fixes the small rule set needed for interoperability without dictating tooling. The claimed novelty is the spec, not the shape.

## Reference Tooling (Deliberately Disposable)

The `okf/` repo ships two proofs-of-concept explicitly framed as replaceable — "the format is the contribution; this agent and the visualizer exist to make the format tangible at both ends":
- **Reference producer agent** — a Python agent with a *BQ pass* (one OKF doc per BigQuery concept from metadata) and a *web pass* (LLM crawls seed URLs to enrich concepts or mint `references/<slug>` docs), with hard page caps and same-domain host filtering.
- **Reference consumer/visualizer** — a `visualize` command that renders any bundle as a single self-contained HTML file (Cytoscape.js force-directed graph + marked markdown), with type filters, search, and "cited by" backlinks.

Three example bundles (GA4 e-commerce, Stack Overflow, Bitcoin) are checked in to demonstrate the format end-to-end.

## Versioning

This is OKF **v0.1 (draft)**. Future revisions use `<major>.<minor>`: minor bumps add backward-compatible things (new optional fields, new conventional headings); major bumps may break (renaming required fields, changing reserved filenames). Bundles may declare their target version via `okf_version` in the bundle-root `index.md`; consumers that don't understand a declared version should attempt best-effort consumption rather than refusing the bundle.
